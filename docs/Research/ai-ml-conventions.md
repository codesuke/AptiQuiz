# AI/ML Agent-Facing Conventions — Research

This document gathers evidence from primary sources (official docs, READMEs, and canonical style guides) on what real-world AI/ML projects typically document as agent-facing conventions, beyond the rendering/data-fetching/caching shape a generic `stack-conventions.md` covers. It feeds a downstream decision (for `docs/agents/stack-conventions.md`, or a dedicated `docs/agents/ai-ml-conventions.md`, or an ADR); it is not itself a decision, per this repo's convention of separating research from ADRs.

## Project Structure & Reproducible Environments

- Cookiecutter Data Science (DrivenData) defines "a logical, reasonably standardized but flexible project structure for doing and sharing data science work," with data folders split by maturity — `raw` (immutable original), `external` (third-party), `interim` (transformed), `processed` (final canonical datasets for modeling) — plus dedicated `models`, `notebooks`, `docs`, and `reports` folders. [Cookiecutter Data Science README](https://github.com/drivendataorg/cookiecutter-data-science/blob/master/README.md)
- Notebooks follow an ordered naming convention: a number for ordering, the creator's initials, and a short dash-delimited description, e.g. `1.0-jqp-initial-data-exploration`. [Cookiecutter Data Science README](https://github.com/drivendataorg/cookiecutter-data-science/blob/master/README.md)
- Reproducibility is anchored by a central `requirements.txt`/`pyproject.toml` for environment specification and a `Makefile` for canonical commands (`make data`, `make train`). [Cookiecutter Data Science README](https://github.com/drivendataorg/cookiecutter-data-science/blob/master/README.md)
- MLflow Projects packages reproducible ML code via an `MLproject` file specifying dependencies (virtualenv/`python_env.yaml`, conda/`conda.yaml`, Docker, or system) and typed entry points, so a run behaves the same "across different environments and platforms." [MLflow Projects docs](https://mlflow.org/docs/latest/ml/projects/)
- Azure ML best practice: jobs submitted from a Git-backed folder automatically track repository metadata for reproducibility, and experiment inputs/outputs are versioned through datasets, model management, and environment management capabilities. [Azure ML best practices (AKS)](https://learn.microsoft.com/en-us/azure/aks/best-practices-ml-ops)

## Model & Dataset Versioning

- DVC treats data and models as first-class versioned artifacts alongside code: ".dvc files" are lightweight metafiles committed to Git while actual data/model bytes live in remote storage (S3, HDFS, SFTP, etc.), producing "a single history for data, code, and ML models that you can traverse — a proper journal of your work." [DVC: Versioning Data and Models](https://doc.dvc.org/example-scenarios/versioning-data-and-models)
- DVC pipelines (`dvc.yaml`, `dvc.lock`) describe which commands generate which pipeline results, and storing these in Git makes ML workflows reviewable via ordinary pull requests, giving "an immutable audit trail." [DVC docs](https://doc.dvc.org/example-scenarios/versioning-data-and-models)
- MLflow Model Registry auto-increments model versions on re-registration under the same name, letting teams "compare iterations, roll back to previous states, and manage multiple versions in parallel (e.g., staging vs. production)." [MLflow Model Registry](https://mlflow.org/docs/latest/ml/model-registry/)
- Rather than rigid lifecycle stages, MLflow favors mutable **aliases** (e.g. `@champion`, `@production`) that point at a specific version and can be reassigned without redeploying infrastructure — the same alias pattern MLflow also uses for prompts (see below). [MLflow Model Registry](https://mlflow.org/docs/latest/ml/model-registry/)
- Every registered model version links back to "the MLflow run, logged model or notebook that produced it," preserving lineage to the datasets, parameters, and training methodology used. [MLflow Model Registry](https://mlflow.org/docs/latest/ml/model-registry/)
- Google Cloud's MLOps guide calls this same idea "Metadata Management": recording pipeline/component versions, execution timestamps, parameter arguments, and pointers to produced artifacts "to help with data and artifacts lineage, reproducibility, and comparisons." [Google Cloud: MLOps continuous delivery and automation pipelines](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)

## Experiment Tracking

- MLflow experiment tracking logs four things per run — parameters, metrics, artifacts, and code version — because "each run records metadata (various information about your run such as metrics, parameters, start and end times) and artifacts (output files from the run such as model weights, images, etc)." Runs nest under experiments, and `mlflow.log_input()` links a run to the dataset it trained on for traceability. [MLflow Tracking docs](https://mlflow.org/docs/latest/ml/tracking/)
- Weights & Biases logs the same four categories — config (hyperparameters via `wandb.Run.config`), metrics (`wandb.Run.log()`), artifacts (model weights, prediction tables via `run.log_artifact()`), and system metrics — organized hierarchically as runs → projects → team entities. W&B explicitly states experiment tracking "saves everything you need to reproduce models later — the latest git commit, hyperparameters, model weights, and even sample test predictions." [W&B Experiments overview](https://docs.wandb.ai/models/track)
- Google Cloud's MLOps guide frames "Experimental-operational symmetry" as a design goal: "the pipeline implementation that is used in the development or experiment environment is used in the preproduction and production environment," so tracked experiment metadata stays comparable to production runs. [Google Cloud: MLOps continuous delivery and automation pipelines](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)

## Evaluation Harness & Regression Tracking

- EleutherAI's `lm-evaluation-harness` versions every task definition: "All tasks have a VERSION field... so that if the task definition changes (i.e to fix a bug), then we can know exactly which metrics were computed using the old buggy implementation to avoid unfair comparisons," enforced with unit tests that pin task behavior. Reported results are expected to cite the task version used. [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness/) (via search of official repo/README content)
- OpenAI's `evals` framework treats evals as regression tests for LLM behavior: "model outputs change when you modify prompts, switch models, or adjust parameters," and "quantitative evals provide useful benchmarks for automated regression testing." Contributors are steered to existing YAML/JSON eval templates rather than bespoke code, and the eval registry itself is versioned via Git-LFS. [OpenAI Evals README](https://github.com/openai/evals) / [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- Google's Rules of ML dedicates its whole final section to this: Rule #37 "Measure Training/Serving Skew" breaks skew into training-vs-holdout, holdout-vs-next-day, and next-day-vs-live-data gaps; Rule #33 says a model trained on data through a cutoff date should be validated against data collected *after* that date so evaluation reflects production reality, not a leaked/optimistic split. [Google: Rules of Machine Learning](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Rule #5, "Test the infrastructure independently from the machine learning," calls for verifying that data flows into training correctly and that a model produces identical scores in training vs. serving — an infra-level regression check distinct from model-quality evals. [Google: Rules of Machine Learning](https://developers.google.com/machine-learning/guides/rules-of-ml)
- Google Cloud's MLOps guide distinguishes **offline model validation** (evaluating metrics on held-out test data, compared against a baseline/production model) from **online model validation** (canary or A/B deployment before full traffic promotion) as two distinct regression gates before a model ships. [Google Cloud: MLOps continuous delivery and automation pipelines](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)

## Data & Model Documentation (Cards)

- Hugging Face model cards are a Markdown `README.md` with a YAML metadata header; the docs state a model card "should describe: the model; its intended uses & potential limitations, including biases and ethical considerations...; the training params and experimental info...; which datasets were used to train your model; the model's evaluation results," and call cards "essential for discoverability, reproducibility, and sharing." [Hugging Face: Model Cards](https://huggingface.co/docs/hub/en/model-cards)
- Hugging Face dataset cards follow the same README+YAML pattern and exist "to inform users about how to responsibly use the data," including documenting "any potential biases within the dataset." [Hugging Face: Dataset Cards](https://huggingface.co/docs/hub/en/datasets-cards)
- Google Research's Data Cards Playbook defines 15 documentation themes for datasets, including Provenance (collection methods, source relationships, versions), Sensitive Attributes (intentional and unintentional sensitive data collection), Access & Retention (availability, data lifecycle policies), and Transformations (processing operations applied) — explicitly aimed at capturing "essential facts about various aspects of ML datasets" that "are not traditionally captured in technical dataset documentation." [Data Cards Playbook](https://sites.research.google/datacardsplaybook/)

## Data Privacy / Security Boundaries in ML Pipelines

- NIST's AI Risk Management Framework (AI RMF 1.0) organizes risk management around four functions — GOVERN, MAP, MEASURE, MANAGE — applied across the AI/data lifecycle; NIST publishes a dedicated companion, the Generative AI Profile (NIST-AI-600-1), specifically to "help organizations identify unique risks posed by generative AI," including data-related risks. [NIST AI RMF overview](https://www.nist.gov/itl/ai-risk-management-framework)
- Google's guidance for handling sensitive data in ML pipelines is concrete and blunt: remove all PII from datasets, and confirm model/data repositories are not set up as world-readable. [Google: AI and ML ethics and safety](https://developers.google.com/machine-learning/managing-ml-projects/ethics)
- Even Google's foundational "Rules of ML" — a rules doc otherwise focused on infra and modeling — flags privacy as a constraint on ordinary debugging practice: Rule #5 qualifies manual data inspection with "where privacy permits, manually inspect the input to your training algorithm," i.e. treat direct human eyes-on-data as something that must be gated by privacy status, not a default debugging step. [Google: Rules of Machine Learning](https://developers.google.com/machine-learning/guides/rules-of-ml)

## Prompt/Config Versioning for LLM-Based Features

- MLflow's Prompt Registry treats prompts as versioned, registry-managed artifacts distinct from but linked to model versions: "Prompt versions in MLflow are immutable, providing strong guarantees for reproducibility," each version carrying a commit message, tags, and optional model config (temperature, max_tokens, provider params). [MLflow Prompt Registry](https://mlflow.org/docs/latest/genai/prompt-registry/)
- Prompt aliases (e.g. `@production`, `@staging`, reserved `@latest`) work exactly like model-registry aliases — mutable pointers to an immutable version — enabling "A/B testing and roll-backs" of prompts without code changes, and prompts integrate with MLflow's tracing/evaluation/monitoring stack for lineage back to the runs and evals that validated them. [MLflow Prompt Registry](https://mlflow.org/docs/latest/genai/prompt-registry/)
- This mirrors the model-registry versioning convention above: LLM-based features need the same "immutable version + mutable alias + linked evaluation" discipline applied to prompts/configs, not just to model weights.

## Recommendation

The following is evidence supplied for a downstream decision — whether and how to add a `docs/agents/ai-ml-conventions.md` to this template. Per `AGENTS.md`, any resulting convention change or hard-to-reverse decision should be recorded separately (in `docs/agents/stack-conventions.md` and/or a new ADR in `docs/ADR/`), not decided here.

If Starter-Pack adds AI/ML-specific agent-facing conventions, the sources above suggest it should cover, at minimum:

- **Data/model versioning discipline**: how raw/interim/processed data and trained model artifacts are tracked (e.g. DVC-style `.dvc`/`dvc.yaml` files or an equivalent), and the rule that data/model bytes never live directly in the main git history the way code does.
- **Experiment tracking minimums**: what must be logged per run (params, metrics, artifacts, code version/git commit, and the dataset version used) so any run is reproducible from its record alone — regardless of which tool (MLflow, W&B, or none) a given project adopts.
- **Model & dataset documentation**: a lightweight model-card/dataset-card expectation (intended use, training data, known limitations/biases, eval results) for any model or dataset an agent introduces, rather than shipping a model with no documentation trail.
- **Evaluation harness & regression gate**: a named, versioned eval suite that must run (and not regress) before a model/prompt change is considered done — mirroring how `code-quality.md` requires `/smell` before a PR; eval task definitions themselves should be versioned so a "fixed" eval doesn't silently invalidate historical comparisons.
- **Training/serving skew check**: an explicit reminder (per Google's Rules of ML) to validate a model against data collected *after* its training cutoff, and to test data-loading infrastructure independently from model quality.
- **Data privacy boundary**: an explicit, non-optional rule that PII must be stripped or the dataset flagged as sensitive before an agent touches it, data/model storage must not be world-readable, and manual "look at the training data" debugging is only permitted where privacy status allows it.
- **Prompt/config versioning for LLM features**: if the project builds LLM-based features, prompts and generation configs should be versioned and alias-tagged the same way model artifacts are, with lineage back to the evals that validated them — not hand-edited inline in application code with no history.
- **Reproducible environments**: a pinned dependency/environment spec (equivalent to an `MLproject` file or a lockfile) for any training or evaluation code, so a run can be repeated by another agent or a CI job later.
